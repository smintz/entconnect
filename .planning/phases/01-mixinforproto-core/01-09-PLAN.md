<objective>
Close the root cause behind three of the four verified gaps.

01-VERIFICATION.md's own closing observation: *"every one of them is invisible to the current test
suite specifically because the corpus avoids the exact shape that triggers it"* — no repeated
scalar fixture, every format-validator fixture single-field, no `optional string` + `required`
fixture. Five green waves, a full golden suite and `go test -race -count=5` told us nothing.

Plans 01-06 and 01-08 patch the three code paths and add the three missing fixtures. That leaves
the generator of the problem entirely intact: the next mapping feature will land with a fixture
that likewise avoids its own failure shape, and the suite will be just as green and just as
uninformative.

This plan makes absence-of-coverage a *detectable* condition. It adds three structural guards over
the corpus — one per axis that has already produced a defect — each of which fails loudly when a new
branch, a new translation outcome, or a new corpus message arrives without coverage. Then it proves
all three actually fire, using the same discipline this gap-closure round applies everywhere: a gate
never observed failing is indistinguishable from no gate.

Purpose: this is the only item in the gap-closure set that reduces the probability of the NEXT
gap rather than closing a current one. It is the deliverable, not test cleanup appended to a fix.

Output: `mixinforproto/corpus_test.go`, three guards with recorded detection proofs, and a written
convention a contributor meets before the guard does.
</objective>

## Executor environment facts (verified live at plan time, 2026-08-08)

1. **`protoregistry.Files` exposes both `RangeFiles` and `RangeFilesByPackage`** in
   `google.golang.org/protobuf@v1.36.11` (`reflect/protoregistry/registry.go` lines 350 and 385).
   `RangeFilesByPackage(protoreflect.FullName("mixinforprototest.v1"), fn)` is the registry walk
   these guards are built on. `google.golang.org/protobuf` is already a direct dependency; nothing
   new is added to `go.mod`.
2. **The corpus package is already linked into the test binary.** `fieldmap_test.go` and
   `validate_test.go` both import `mixinforprototestv1`, so every corpus file has registered itself
   by the time any test runs. No extra blank import is required, though adding one explicitly in
   `corpus_test.go` makes the dependency self-evident and is preferred.
3. **Proto map fields generate synthetic nested map-entry messages.** `maps.proto`'s three map
   fields each produce one. They are real `MessageDescriptor`s in the registry and MUST be filtered
   out via `md.IsMapEntry()`, or the coverage map in Task 3 will demand entries for messages no
   human wrote.
4. **Nested messages must be walked recursively.** `md.Messages()` on each top-level message; the
   corpus does not currently declare hand-written nested messages, but the walk must not assume that
   — assuming it is the exact class of mistake this plan exists to prevent.
5. **Build the guards on `classify` / `classifyRequired` / `resolvedFieldRules` directly, never on
   `derive`.** Several corpus messages deliberately fail derivation (`Oneofs` without `Exclude`,
   `reserved.proto`'s collision fixtures, and after plan 01-06 the `Repeated*` messages). A guard
   built on `derive` would either skip them or drown in expected errors.
