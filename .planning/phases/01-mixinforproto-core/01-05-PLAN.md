<objective>
Relay the protovalidate constraints that have an exact ent equivalent into real ent builder calls,
and record everything else as residual provenance rather than silently dropping or approximating it.

Purpose: this is why the mixin exists. Mutations do not only originate from RPC — flows, workers,
seeds, tests and CLIs all mutate through the ent client, so the boundary interceptor is UX and the
schema is the guarantee. Both are generated from the same protovalidate source, so they must not be
able to disagree. Tier 1 makes the agreeing subset visible to the rest of the ecosystem
(`entoas`/`entgql`/doc generators see `MaxLen`); the residual record is the honest handoff for
everything else.

Output: a validation relay that is exactly as strong as it claims to be, with the gap written down.
</objective>

## Reconciliation applied in this plan

- **R5 — NEW, discovered at plan time: `mixinforproto.md` §4.1's Tier 1 table is wrong about string
  length units.** The design doc's normative table maps `string.min_len` / `max_len` / `len` directly
  onto ent's `MinLen` / `MaxLen`. Verified this session against both sources:
  - `buf.validate`'s `StringRules.min_len` documents "the specified number of characters (Unicode
    code points), **which may differ from the number of bytes in the string**".
  - `entgo.io/ent@v0.14.6` `schema/field/field.go:216` implements `MinLen(i)` as `len(v) < i` — a
    **byte** comparison on a Go string.

  These disagree for any non-ASCII value. Three emoji are 3 code points but 12 bytes: protovalidate
  `max_len: 5` accepts that string and ent `MaxLen(5)` rejects it. That is precisely the
  boundary-versus-schema disagreement the entire design exists to make impossible, and Phase 3's
  differential harness (PIPE-06) is built to catch exactly this class — so it must not be knowingly
  shipped now. Note the byte-semantic siblings **do** match exactly and are safe Tier 1:
  `string.min_bytes` / `max_bytes` / `len_bytes`, and `bytes.min_len` / `max_len` / `len`.

  Task 1 is a `checkpoint:decision` on how to resolve it. This is the same trade CONTEXT.md's own
  discretion list ranks first (D-13, introspectability versus verdict identity), now with a concrete
  verified instance attached.
- **R1 (inherited):** Tier 1 needs only `buf.build/go/protovalidate`'s constraint enumeration, never
  CEL compilation, so **no cel-go dependency is added by this plan**. Residual CEL expression strings
  are fingerprinted as text, never compiled — compilation is Phase 3.
- **R4 (inherited):** golden assertions go through the `fieldproj` projection, never a raw
  `field.Descriptor` marshal — this plan is the first to attach validators broadly, which is exactly
  when a raw marshal would start failing.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Denial of Service | `regexp` compile on a contract-supplied `pattern` (ReDoS) | medium | mitigate | Go's `regexp` is RE2: it guarantees linear-time matching and admits no catastrophic backtracking, so a pathological contract pattern cannot cause exponential blowup either at compile or at match time. This is a structural property of the engine, not a check that can be forgotten. Compilation is additionally error-checked rather than `MustCompile`-panicking, so a malformed pattern becomes a named schema-load failure. D-13 further delegates format validators to protovalidate's own expressions rather than hand-written ones, inheriting upstream's posture instead of introducing a new one. |
| T-01-22 | Tampering | Tier 1 translation silently weaker than the contract | high | mitigate | A translated constraint that accepts a value protovalidate rejects is a silent security control failure: the boundary enforces the real rule and the storage layer does not, so any non-RPC mutation path (flow, worker, seed, CLI) bypasses it. Three specific guards, each with a test: floats are never widened (D-12); integer adjustments are overflow-guarded so a bound cannot invert; and the R5 length-unit mismatch is resolved explicitly rather than assumed. Blocking-threshold threat — this is the phase's core correctness property. |
| T-01-23 | Repudiation | an untranslatable constraint silently dropped | high | mitigate | A dropped constraint leaves a field looking validated when it is not, and loses the data Phase 3 needs to execute it. D-11 requires recording, never dropping; the acceptance criteria assert that every resolved rule appears in exactly one of `TranslatedIDs` or `ResidualIDs` and never in neither. Blocking-threshold threat. |
| T-01-24 | Tampering | residual fingerprint collision or instability | medium | mitigate | The fingerprint is Phase 5's drift-detection input, so an unstable one produces false drift and a weak one could mask a changed rule. SHA-256 over sorted expression text is collision-resistant and order-independent; a test asserts stability across five runs and sensitivity to a changed expression. |
| T-01-25 | Denial of Service | CEL expression text handled as data at schema load | low | accept | Residual expressions are hashed as text and never compiled or evaluated in this phase, so no CEL evaluation cost or sandbox concern exists yet. Accepted for Phase 1; transferred to Phase 3's security pass when the expressions actually execute. |
| T-01-26 | Information Disclosure | constraint IDs and expression fingerprints in annotations | low | accept | Constraint IDs are contract structure already public in the `.proto`; the fingerprint is a one-way hash of expression text, not the text itself. No field values pass through. Accepted. |
