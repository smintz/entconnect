## Phase Goal

> **Goal (verbatim from ROADMAP.md, Phase 2):** Developers get generated ConnectRPC CRUD
> handlers wired directly to the ent client, with safe partial updates and a fixed,
> privacy-aware interceptor chain — no hand-written handler code, no ent client leakage.

**MVP_MODE planner note:** the ROADMAP `**Goal:**` line for Phase 2 is not in
`As a … I want to … so that …` user-story form; per MVP-mode rules the planner does not invent
one. Run `/gsd mvp-phase 02` if a user-story framing is wanted.

<objective>
Widen the proven slice to the write path: **Create end to end, then Delete end to end.** Each task
adds one RPC that a real Connect client can call against a real ent client, reusing the interceptor
chain, error mapping, and hook-based emission the tracer already proved.

Purpose: CRUD-02 — Create and Delete operate directly against the ent client, inside the same fixed
chain, with mutation errors mapped by the same D-18 table that Get uses for reads. This is where
the error table stops being a read-only concern: constraint violations and privacy denials on
mutations are the first mutation-shaped failures the mapping has to get right.

Output: two per-verb generators registered into the existing registry, their templates, a
service-bearing write corpus, and a self-contained fixture app with two real round-trip tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Connect client → generated mutation handler | Untrusted request bodies reach a write path; the protovalidate stage and the contract's own rules are the only inspection point |
| Generated mutation body → ent client | The identifier and field values the mutation applies come from the request; ent privacy policies are the authorization point and only see the context the chain injected |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-08 | Tampering | Generated Delete body | high | mitigate | The generator renders a by-primary-key delete only; an acceptance criterion negative-greps the committed emitted file for a predicate-free bulk delete builder call, and a test asserts an unrelated row survives. |
| T-02-09 | Elevation of Privilege | Generated Create and Delete bodies | high | mitigate | Every ent builder call receives the handler's request context, so `privacy.Policy.EvalMutation` sees the injected viewer; asserted by source inspection (`.Save(ctx)`/`.Exec(ctx)`, no `context.Background()`) plus a `CodePermissionDenied` test on each verb. |
| T-02-10 | Information Disclosure | Constraint-violation errors on Create | medium | mitigate | `ent.IsConstraintError` maps to `CodeAlreadyExists` with no driver text forwarded; anything unrecognised stays `CodeInternal` with the detail logged only (D-18). RESEARCH A4's unique-vs-FK ambiguity is recorded in `runtime/errormap.go`, not silently widened. |
| T-02-11 | Tampering | Proto3 zero-collapse mass assignment on Create | medium | accept | On Create, setting every contract field from the request is the correct semantic — the zero-collapse hazard is specific to partial updates and is mitigated by the FieldMask gating in plan 02-04. Accepted here with that pointer. |
| T-02-12 | Denial of Service | Unbounded write volume | low | accept | Rate limiting is not in this phase's scope and no requirement asks for it; ASVS L1 does not mandate it at the handler-generation layer. |
