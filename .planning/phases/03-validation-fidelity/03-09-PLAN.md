Close the single remaining gap in `03-VERIFICATION.md` (`status: gaps_found`, `score: 7/8`,
`gaps_remaining: []` for all five prior findings): **`buf.validate.oneof` (`OneofRules`) is a
third, independent protovalidate rule-carrier extension that `mixinforproto` never resolves,
never records, and that neither of 03-08's declaration-surface guards can see.**

This is NOT the `MessageRules.oneof` carrier (`MessageOneofRule`) that 03-08 closed under the
same "CR-01" label. Verified directly against this repository's vendored
`proto/buf/validate/validate.proto`: `MessageOneofRule` is declared **inside** `message
MessageRules` (carrier field 4); `OneofRules` is a **separate top-level message** extended onto

descriptor and Guard B walks `FieldRules`' own descriptor — `OneofRules` is a third message that
neither enumerates, so its single declared member is invisible **by construction**, not merely
unexempted.

**Impact today:** a contract declaring `(buf.validate.oneof).required = true` loads cleanly and
any write reaching the generated `ent.Client` directly (background jobs, migrations, internal
callers bypassing the RPC boundary) persists an entity violating that constraint, with zero
record anywhere that this is possible. That falls squarely inside this phase's invariant #5
("unhandled rule carriers must fail loudly ... never silently downgrade a field to unvalidated
at the storage layer") and is a fourth, structurally distinct counterexample to Success
Criterion 2's "a caller cannot tell which layer caught it".

**MVP user story** (ROADMAP Phase 3 `**Mode:** mvp`):
**As a** developer whose contract declares a required oneof, **I want to** be told — in the same
machine-readable provenance channel every other unenforceable rule already uses — that this
constraint lives only at the RPC boundary, **so that** I can write the storage-side safety net
deliberately instead of discovering the hole from corrupt rows.

Purpose: D-09 is the decision that governs this ("be loud about the adopter's bugs, honest about
our own" — an unbindable carrier is *recorded*, not panicked on). D-10/MIX-10 is why storage
enforcement is not merely deferred but structurally unavailable. D-24 governs the output order.

Output: `ResolveOneofRules` wired into `derive.go`'s per-message walk, an additive
oneof-naming key and reason constant on the annotation contract, a corpus fixture declaring
`(buf.validate.oneof)`, a third declaration-surface exhaustiveness guard, a named test asserting
the storage-layer omission is deliberate, and a real-`ent.Client` proof that the resulting
boundary/storage divergence is exactly the one provenance records.

## The fix-option (a)-vs-(b) choice, stated explicitly

`03-REVIEW.md`'s CR-01 offers two acceptable fixes, and `03-VERIFICATION.md`'s `missing:` list
repeats them: **(a)** resolve `OneofRules` and record it into `SourceMessage.BoundaryOnly` with
a new reason naming the oneof, or **(b)** document the omission as a deliberate v1 scope
boundary with a named test asserting it is intentional. Silence is the one option this
codebase's own `constraintClassExceptions` convention rules out.

**This plan takes (a), scoped to provenance recording rather than storage enforcement, and
carries (b)'s documentation-and-named-test discipline alongside it.**

Rationale — three independent reasons, all verified against the tree, not assumed:

1. **Storage enforcement is structurally impossible here, not merely hard.**
   `checkOneofResolution` (`derive.go:324`, MIX-10) already requires **every member of every
   real, non-synthetic oneof** to be `Exclude`d or `Override`n before schema load can succeed.
   So for any schema that loads at all, no oneof member derives an ent field of its own —
   there is nothing at the storage layer for a "exactly one of these is set" check to read.
   Overridden members are replaced by developer-authored `ent.Field`s whose relationship to the
   proto oneof is opaque to this package by design. This is not a difficulty judgment; it is a
   structural property of an existing, shipped gate.

2. **`OneofRules.required` is cross-field in spirit, and this codebase already places
   cross-field rules boundary-only by default.** `mixinforproto.md` §4.3 is normative that
   message-level rules are boundary-only unless a developer opts in with
   `WithMessageRules(OnCreate)`, and D-10 records that an opt-in referencing an unavailable
   field is a schema-load failure precisely because a verdict computed from data that was never
   real is worse than no verdict. A required-oneof check over excluded members would be exactly
   that phantom verdict.

3. **D-09 names this case directly.** "Unbindable field kind → record as still-unenforced /
   boundary-only in provenance. That defect is *ours*, not the contract's, and panicking would
   brick a schema that loaded fine under Phases 1-2. Recording it keeps it visible to Phase 5's
   drift check." `BoundaryOnlyUnbindable`'s own doc comment describes exactly this shape.

**Reversibility: `one-way`.** `SourceMessage`/`BoundaryOnlyRule` is a published JSON contract
that crosses entc's schema-load subprocess boundary and that Phase 5's drift check is designed
to consume; `annotation.go`'s reason constants are documented as a closed set that is
"never renamed or repurposed once shipped". Adding a key and a reason value is permitted by
`ContractVersion = 1`'s additive-only policy, but the value itself cannot be withdrawn once a
consumer switches on it. Task 0 gates that door.

**The two non-blocking warnings in `03-VERIFICATION.md`'s Anti-Patterns table are FOLDED IN,
not deferred** — `reverseEnum`'s rejected-value interpolation (WR-01) and `README.md`'s stale
`Exclude`/`Override`/`WithMessageRules` claims (WR-02), plus `REQUIREMENTS.md`'s stale
VAL-09/10/11 checkboxes. They are handled in `03-10-PLAN.md` (wave 8), which owns every
documentation file and `reverse.go`, so its file set stays disjoint from this plan's. Neither
is dropped and neither is deferred past this phase.
</architectural_decision>
