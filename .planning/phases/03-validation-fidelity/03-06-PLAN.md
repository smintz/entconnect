<objective>
Close verification gaps **CR-02** and **CR-03** from `03-VERIFICATION.md` — the two
counterexamples that live inside `buildHookState`'s per-field loop.

Both have one cause: the loop reasons about **the field descriptor alone**, never about
`(buf.validate.field).ignore` and never about the `Option` set the mixin was constructed
with. The boundary interceptor's own protovalidate evaluator handles both correctly, so
every field carrying either produces a **divergent verdict** — the exact property
ROADMAP Phase 3 Success Criterion 2 promises cannot happen.

**MVP user story** (ROADMAP Phase 3 `**Mode:** mvp`, Goal line reframed):
**As a** developer adopting `MixinForProto`, **I want to** have `ignore`, `Exclude(...)`
and `Override(...)` mean the same thing at the storage layer that they already mean at
the RPC boundary, **so that** I cannot ship a schema that loads cleanly and then rejects
(or accepts) writes the boundary would not.

Purpose: SC2's "a caller cannot tell which layer caught it" is currently false for three
concrete rule shapes; two of them are fixed here. D-02 (protovalidate authoritative for
every rule on an in-scope field), D-03 (per-field evaluation), D-07/D-08 (the hybrid split
drawn by rule kind) and D-12 (fail closed, never a fabricated constraint ID) all constrain
the fix.

Output: a new `ignore` corpus fixture with regenerated stubs, an ignore-aware and
option-aware `buildHookState`/`evaluate`, unit tests pinning both behaviours, and real
`ent.Client` differential proofs so the PIPE-06 sweep is no longer blind to either shape.
</objective>
